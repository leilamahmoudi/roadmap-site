# Phase 2: Assign Roles

> The role you give Claude at the start of a session shapes everything that follows. A focused identity produces sharper output than a blank-slate prompt. Switch roles when the type of work switches.

---

## 1. Match the Role to the Task

Different tasks need different identities. A session focused on data modeling calls for a different role than one writing user-facing copy.

| Task type | Example role |
|---|---|
| Backend logic | Senior backend engineer, specializing in [stack] |
| Frontend / UI | Senior frontend engineer with a focus on accessibility |
| Database design | Database architect familiar with [Postgres / SQLite / etc.] |
| Security review | Security engineer reviewing for OWASP top 10 |
| Documentation | Technical writer for a developer audience |

---

## 2. Write the Role Prompt

Keep it to two or three sentences. State the role, the relevant expertise, and any behavioral constraints.

```
You are a senior [specialty] engineer. You write clean, minimal code and
flag anything that looks like scope creep. You do not refactor code that
is not directly related to the current task.
```

---

## 3. Stack It With Context

Role goes first, then the starting prompt from Phase 1, then the task. Order matters: Claude reads top to bottom, and identity should be set before context is loaded.

```
You are a senior [role] working on [project name].

Before doing anything:
1. Read project-owner-expectations.md
2. Read the current task below

Current task: [task]
```

---

## Summary

- Assign a role at the start of every session, not just the first one.
- Match the role to the type of work in that session.
- Role first, then context, then the task.
- Consistent roles reduce drift across sessions.
