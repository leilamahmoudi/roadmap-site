# Phase 2: Assign Roles

Now define the specialist roles that would normally exist around a product like this, such as product, UX, architecture, security, or engineering.

Using `project-owner-expectations.md`, Claude should determine which specialist perspectives are actually relevant to this project. We don't want a fixed list of roles. The roles should be generated based on what we're building.

## For Each Role, Define

| Area                   | What it captures                                                       |
| ---------------------- | ---------------------------------------------------------------------- |
| **Lens**               | What this specialist pays attention to when evaluating decisions       |
| **Quality bar**        | What needs to be true for them to consider the solution good enough    |
| **Decision ownership** | Which decisions this role should influence or own                      |
| **Pushback**           | What this specialist would challenge or question before implementation |

The goal is not to have Claude pretend to be a group of people. These roles should create **concrete constraints and quality criteria** that can guide architecture, implementation, and review.

## Example Prompt

Read `project-owner-expectations.md` and identify the specialist roles that would realistically be involved in building this product.

Do not use a fixed list of roles. Choose only the roles that are relevant to this specific project.

For each role, define:

* their lens
* their quality bar
* the decisions they own or influence
* what they would push back on

Keep the roles practical and avoid unnecessary roles or process.

Use these perspectives to establish concrete constraints and quality criteria for the next stages of the project.
